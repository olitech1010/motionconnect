## 1. Executive Summary

Motion Connect is a **campus WiFi management platform** that enables educational institutions running MikroTik hotspot infrastructure to sell internet access to students via Hubtel Mobile Money. The platform replaces the traditional "static HTML on the router" approach with a **Next.js cloud application** (hosted on Vercel) that serves as both the captive portal frontend and the secure backend — keeping payment API keys off-device and enabling transaction tracking, admin dashboards, and future scalability.

The MikroTik RB5009UG+S+ router (RouterOS 7.19.6) is accessible via a **static public IP** from Starlink. The Next.js backend communicates with the router's REST API over this public IP to create **Hotspot Users** after successful Mobile Money payments.

The client designed the initial captive portal UI in `login.html`. We will use it as **design inspiration** and **improve** the interface while preserving the brand identity and user flow.

### 2.2 Student Journey (Happy Path)

```
1. Student connects to campus WiFi SSID
2. MikroTik intercepts → serves redirect login.html
3. Redirect sends student to:
   https://motionconnect.vercel.app?mac=XX&ip=XX&link-login=XX&link-orig=XX
4. Student sees captive portal (Next.js on Vercel)
5. Student selects package → enters MoMo number → taps "Pay"
6. Backend:
   a. POST /api/payments/initiate → calls Hubtel Receive Money API
   b. Creates Transaction (status: pending) in Supabase Postgres
   c. Returns {reference} to frontend
7. Frontend polls GET /api/payments/status?reference=XXX
8. Student approves MoMo prompt on their phone
9. Hubtel sends webhook → POST /api/payments/webhook
   a. Verify signature
   b. Update Transaction (status: success)
   c. Call MikroTik REST API → create Hotspot User:
      • username: generated voucher code
      • password: random
      • profile: matches package (e.g. "weekly")
      • mac-address: student device MAC
      • limit-bytes-total: data cap in bytes (e.g. 5368709120 for 5GB)
      • comment: "Motion Connect | txn: REF-XXX"
   d. Mark transaction.mikrotik_synced = true
10. Frontend receives credentials → shows Credentials Card
11. Pre-fills MikroTik login form → auto-submits to router
12. MikroTik authenticates Hotspot User → internet access granted
13. MikroTik enforces BOTH:
    • Session timeout (e.g. 7 days)
    • Data cap (e.g. 5GB via limit-bytes-total)
    Whichever limit is hit first → user disconnected
```

### 2.3 MikroTik Hotspot User Enforcement

**Method: Hotspot Users** (standard MikroTik approach)

When a student pays, the backend creates a **Hotspot User** on the router:

```
/ip/hotspot/user/add
  name=MC-A7X9B2
  password=k9m2p5
  profile=weekly
  mac-address=AA:BB:CC:DD:EE:FF
  limit-bytes-total=5368709120
  comment="Motion Connect | txn: REF-20260725-001"
```

The **Hotspot User Profile** controls rate limits and session duration:

```
/ip/hotspot/user/profile
  name=weekly
  rate-limit=5M/5M
  session-timeout=7d
```

**What MikroTik enforces automatically (no backend needed):**
- Speed limits via `rate-limit` on the profile
- Session duration via `session-timeout` on the profile
- Data cap via `limit-bytes-total` on the user
- MAC binding via `mac-address` on the user
- When either time OR data is exhausted → user is disconnected → sees portal again

### 4.5 REST API Setup

```routeros
# Enable REST API
/ip service set www-ssl disabled=no port=443
/certificate add name=local-cert common-name=router.local
/ip service set www-ssl certificate=local-cert

# Dedicated API user
/user add name=motion-api password=<strong-password> group=full

# Firewall: restrict REST API access
/ip firewall filter
add chain=input dst-port=443 protocol=tcp src-address-list=vercel-ips action=accept comment="Allow Vercel API access"
add chain=input dst-port=443 protocol=tcp action=drop comment="Block all other REST API access"
```

### 4.6 Port Forward (Starlink Static IP)

On the Starlink router / upstream gateway, forward:
- **External port 443** → **192.168.20.1:443** (MikroTik REST API)

> ⚠️ **WARNING**: The REST API port should be restricted via firewall rules (Section 4.5) to only accept connections from Vercel's IP ranges.

## 5. Database Schema (Supabase PostgreSQL)

### 5.1 SQL Schema Migration (`001_initial_schema.sql`)

```sql
-- Enable UUID extension
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Packages table
CREATE TABLE public.packages (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name TEXT NOT NULL,
  slug TEXT UNIQUE NOT NULL,
  data_limit TEXT NOT NULL,
  data_limit_bytes BIGINT NOT NULL,
  duration_label TEXT NOT NULL,
  duration_seconds INTEGER NOT NULL,
  amount DECIMAL(10, 2) NOT NULL,
  mikrotik_profile TEXT NOT NULL,
  signal_bars INTEGER NOT NULL DEFAULT 1 CHECK (signal_bars BETWEEN 1 AND 5),
  is_active BOOLEAN NOT NULL DEFAULT true,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Transactions table
CREATE TABLE public.transactions (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  reference TEXT UNIQUE NOT NULL,
  hubtel_reference TEXT,
  package_id UUID REFERENCES public.packages(id) ON DELETE SET NULL,
  package_name TEXT NOT NULL,
  amount DECIMAL(10, 2) NOT NULL,
  phone TEXT NOT NULL,
  mac_address TEXT NOT NULL,
  ip_address TEXT,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'success', 'failed', 'expired')),
  payment_method TEXT DEFAULT 'mtn-momo',
  voucher_code TEXT,
  mikrotik_username TEXT,
  mikrotik_synced BOOLEAN NOT NULL DEFAULT false,
  error_message TEXT,
  sms_status TEXT CHECK (sms_status IN ('sent', 'failed', NULL)),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Routers table
CREATE TABLE public.routers (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name TEXT NOT NULL,
  campus TEXT NOT NULL,
  ip_address TEXT NOT NULL,
  api_port INTEGER NOT NULL DEFAULT 443,
  api_username TEXT NOT NULL,
  api_status TEXT NOT NULL DEFAULT 'unknown' CHECK (api_status IN ('online', 'offline', 'unknown')),
  router_model TEXT DEFAULT 'RB5009UG+S+',
  router_os_version TEXT DEFAULT '7.19.6',
  last_checked TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Settings table
CREATE TABLE public.settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Activity Logs table
CREATE TABLE public.activity_logs (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  action TEXT NOT NULL,
  actor TEXT NOT NULL DEFAULT 'system',
  details JSONB DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Row Level Security (RLS) Policies
ALTER TABLE public.packages ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.transactions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.routers ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.settings ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.activity_logs ENABLE ROW LEVEL SECURITY;

-- Allow public read access to active packages for captive portal
CREATE POLICY "Public can view active packages" ON public.packages
  FOR SELECT USING (is_active = true);

-- Allow public read access to transactions by reference (for status polling)
CREATE POLICY "Public can view transaction status by reference" ON public.transactions
  FOR SELECT USING (true);

-- Authenticated admin users have full access to all tables
CREATE POLICY "Admins have full access to packages" ON public.packages
  FOR ALL TO authenticated USING (true);
CREATE POLICY "Admins have full access to transactions" ON public.transactions
  FOR ALL TO authenticated USING (true);
CREATE POLICY "Admins have full access to routers" ON public.routers
  FOR ALL TO authenticated USING (true);
CREATE POLICY "Admins have full access to settings" ON public.settings
  FOR ALL TO authenticated USING (true);
CREATE POLICY "Admins have full access to activity logs" ON public.activity_logs
  FOR ALL TO authenticated USING (true);
```

## 6. Edge Cases & Error Handling

| Scenario | Expected System Behavior |
|----------|--------------------------|
| Student closes browser mid-payment | Hubtel webhook still fires → backend creates MikroTik user. Student uses "I have an account" tab next time. |
| Hubtel callback never arrives | Frontend polling times out (120s). Show "contact support" with reference. |
| Duplicate payment for same MAC | Check for active Hotspot User with this MAC before initiating. Warn student. |
| MikroTik unreachable at user creation | `mikrotikSynced = false`. Retry every 30s for 5 min. Alert admin. |
| Data cap exhausted | MikroTik disconnects automatically (`limit-bytes-total`). Student sees portal. |
| Session timeout expires | MikroTik disconnects automatically (`session-timeout`). Student sees portal. |
| iOS/Android captive mini-browser | Detect CNA User-Agent. Show "Open in Safari/Chrome" prompt. |
| MikroTik vars missing from URL | Show: "Please connect to the campus WiFi first." |
| Same device, different student pays | New Hotspot User created with same MAC. MikroTik uses latest. |
| Admin changes package price | Only affects new purchases. Active sessions keep original terms. |

## 7. Non-Functional Requirements

### Performance
- Portal page load: **< 2 seconds** (student has walled-garden-only access)
- `/api/payments/initiate` response: **< 3 seconds** (includes Hubtel API call)
- No external fonts/CDNs on portal — self-contained assets only (walled garden)

### Security
- Hubtel keys: Vercel env vars only, never client-side
- Webhook HMAC verification on all Hubtel callbacks
- Rate limiting: max 3 payment requests per phone per 5 minutes
- Admin auth: Supabase Auth (`@supabase/ssr`) with secure cookies & RLS policies
- MikroTik API creds: server-side env vars only
- Zod validation on all API inputs
- CORS: portal domain only
- MikroTik firewall: REST API restricted to Vercel IPs

### SMS Readiness (Deferred)
- `transaction.sms_status` field exists in PostgreSQL schema
- `services/sms.service.ts` interface defined but not implemented
- Hubtel SMS API or Twilio can be plugged in later

### Scalability
- v1: Single campus, single router, ~500 students
- v2: Operational tools, SMS, analytics
- v3: Multi-campus, multi-router, enterprise
